Run the paper store¶

The paper store sits beside the GEO/SRA store. It holds the papers that the store's Series and BioProjects link to, and the status of each one. One long-running Slurm job, the paper job, keeps it current. Each day it fetches what it can, and once a month it takes in new papers.

Set up once¶

Make the paper store and point it at the GEO/SRA store it reads:

labdata papers init /path/to/paper-store --store /path/to/store \
  --copy-to gcs:<bucket>/datalake/paper-store

Save your logins. The NCBI one fetches PubMed records. The OpenAlex accounts buy paper copies, 100 a day each:

labdata ncbi configure
labdata papers configure

labdata papers configure asks for one email and API key per account. Leave the email blank to finish. Without accounts, the daily pass skips OpenAlex and says so. A running job reads the accounts at each pass, so new ones count from the next pass, with no restart.

For the copy to Google Cloud Storage (GCS), set up the gcs rclone remote and log in as Copy the store to GCS shows. Leave out --copy-to to run with no copy.

Fill the store the first time¶

The first PMC sync takes in every linked paper, so it runs much longer than a monthly one: plan for most of a day. It stores about half a terabyte, mostly supplementary files and figures, so check the free space first. Submit it once by hand, from the repository folder on the cluster, with more CPUs and a longer time limit:

export LABDATA_PAPERS=/path/to/paper-store
df -h "$LABDATA_PAPERS"
sbatch --job-name=labdata-papers-backfill --partition=cpu_batch \
  --cpus-per-task=4 --mem=8G --time=2-00:00:00 \
  --output=labdata-papers-backfill.%j.log \
  --wrap "pixi run labdata papers pmc-sync"

If it stops, submit it again. It goes on from where it stopped. The paper job can start at the same time: it waits until the first sync is done.

To fill the store in rounds, add --sample 0.01, then --sample 0.1, then run it with no --sample. Each round skips the papers the last round looked up this month. A sampled sync does not count as the month's PMC sync: paper-status.json records it as the last pass, with its sample share, but only a sync over all papers sets last_pmc_sync_success. So the paper job still runs the month's PMC sync after a sampled round.

The first copy to GCS sends all of it. Run it once by hand, as its own job, after the first sync ends, so the paper job's daily pass does not wait behind it:

sbatch --job-name=labdata-papers-copy --partition=cpu_batch \
  --cpus-per-task=2 --mem=8G --time=1-00:00:00 \
  --output=labdata-papers-copy.%j.log \
  --wrap "pixi run labdata papers copy"

Log in to rclone first: the login lasts one day. Later copies send only new and changed files, and delete from the bucket what the paper store no longer holds.

Start the paper job¶

export LABDATA_PAPERS=/path/to/paper-store
sbatch scripts/papers/serve.sbatch

The job asks for 2 CPUs and 8 GB on cpu_batch, for the 14 days that partition allows. It runs the daily pass each day after 00:30 UTC, and the PMC sync on the 3rd of each month. Each pass ends with a copy of new and changed files to GCS.

PMC gives the article text, figures and supplements, while OpenAlex and host links give a PDF only. So when a paper fetched from OpenAlex or a host link later appears in PMC, the PMC sync takes its PMC files and then deletes the old PDF.

At start, the job submits the next job, which waits for this one to end and then takes over. So the chain goes on by itself: Slurm on arc accepts a job submitted from inside a running job.

To stop the chain, cancel the waiting job first, then the running one:

squeue --me -n labdata-papers
scancel <waiting job id>
scancel <running job id>

If the chain breaks, submit scripts/papers/serve.sbatch again by hand. A new job does only what is due: a day with no daily pass, or a month with no PMC sync after the 3rd. The job log says successor not submitted when it could not submit the next job.

Watch it¶

The job log, labdata-papers.<job id>.log, prints a line a minute. The first job writes it where sbatch --output says, or into the folder you submitted from. Each next job writes its log into the same folder. Between passes it looks like this:

2026-11-05T07:01Z idle; last daily pass 2026-11-05, last PMC sync 2026-11-03, copy pending: no

Each step can also run alone: labdata papers daily, labdata papers pmc-sync and labdata papers copy.

Read paper-status.json¶

The file at the paper store root says what the job did last and where the papers stand:

{
  "last_pass": {"kind": "daily", "start": "2026-11-05T00:30:02+00:00",
                "end": "2026-11-05T01:12:40+00:00", "outcome": "success"},
  "last_daily_success": "2026-11-05",
  "last_pmc_sync_success": "2026-11-03",
  "fetches": {"date": "2026-11-05", "by_tier": {"openalex": 300, "host": 2}},
  "quota": {"date": "2026-11-05", "by_key": {"a@lab.org": 100, "b@lab.org": 100, "c@lab.org": 100}},
  "counts": {"fetched": {"": 80512}, "waiting": {"openalex-backlog": 7690, "pmc-embargo": 1204},
             "manual": {"no-route": 9300, "host-blocked": 120}, "skipped": {"placeholder": 41}},
  "copy_pending": false,
  "paperpile_pending": false
}
  • last_daily_success older than today, after 00:30 UTC, means a missed day.
  • last_pmc_sync_success is the date of the last PMC sync over all papers. A sampled sync leaves it alone.
  • quota shows the copies each OpenAlex account bought today.
  • counts gives the papers per status, then per reason.
  • copy_pending: true means the GCS login had expired and the bucket is behind. Log in, then run labdata papers copy. A copy that works sets it back to false.

The copy makes the bucket match the paper store. It leaves out paper-status.json, the lock file and the files a pass writes while it runs.

Check the copy¶

Compare the paper store with its copy_to, leaving out the hidden files and the status record, as the copy does:

pixi run rclone check "$LABDATA_PAPERS" <copy_to> --one-way \
  --filter "- .*" --filter "- .*/**" --filter "- /paper-status.json"

It should report 0 differences. Run it between passes: a pass that runs beside it changes files under it.
